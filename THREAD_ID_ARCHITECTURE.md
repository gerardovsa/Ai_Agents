# Thread ID Architecture - Using `thread_slug` Everywhere

## ✅ CORRECT APPROACH: Use `thread_slug` as Primary Identifier

### Why `thread_slug` is the Right Choice:

1. **🎯 User-Facing & Stable**
   - `thread_slug` (e.g., `'1762664086386'`) is a timestamp-based unique identifier
   - Never changes once created
   - Can be shared, copied, bookmarked
   - Works in URLs, APIs, and UI consistently

2. **🔄 Consistent Across Systems**
   - Frontend uses it as `thread.id`
   - APIs accept it as `thread_id` parameter
   - Thread assignments use it
   - Synergy sessions reference it
   - Can be used in other systems (webhooks, integrations, etc.)

3. **🚫 Problems with Using Database `id` (auto-increment)**
   - Changes if database is rebuilt
   - Different values in dev/staging/production
   - Not portable between databases
   - Implementation detail that shouldn't leak to frontend
   - Cannot be generated by frontend before API call

4. **💾 Database Best Practice**
   - Auto-increment `id` is for internal database relationships ONLY
   - External systems should use a stable, unique identifier (UUID or timestamp)
   - Separation of concerns: internal vs external IDs

## 🔧 Implementation Strategy

### **1. Backend Helper Function (Recommended)**

Create a utility function that all backend routes use:

```python
# AI_infrastructure/utils/thread_helpers.py

def get_thread_by_slug(thread_slug: str) -> dict:
    """
    Get thread record by thread_slug (external ID)
    
    Args:
        thread_slug: External thread identifier (e.g., '1762664086386')
    
    Returns:
        dict with thread data including internal 'id' for JOINs
    """
    query = """
        SELECT 
            id as internal_id,
            thread_slug,
            name,
            location,
            message_count,
            ...
        FROM threads
        WHERE thread_slug = ?
    """
    result = execute_sqlite_query(db_path, query, (thread_slug,))
    return result[0] if result else None

def get_messages_for_thread(thread_slug: str) -> list:
    """
    Get all messages for a thread using thread_slug
    
    Args:
        thread_slug: External thread identifier
    
    Returns:
        List of message dicts
    """
    query = """
        SELECT m.*
        FROM messages m
        JOIN threads t ON m.thread_id = t.id
        WHERE t.thread_slug = ?
        ORDER BY m.timestamp ASC
    """
    return execute_sqlite_query(db_path, query, (thread_slug,))

def save_message_to_thread(thread_slug: str, role: str, content: str):
    """
    Save message using thread_slug
    
    Args:
        thread_slug: External thread identifier
        role: 'user' or 'assistant'
        content: Message text
    """
    # Get internal ID
    thread = get_thread_by_slug(thread_slug)
    if not thread:
        raise ValueError(f"Thread not found: {thread_slug}")
    
    internal_id = thread['internal_id']
    
    # Insert message
    query = """
        INSERT INTO messages (thread_id, role, content, timestamp)
        VALUES (?, ?, ?, CURRENT_TIMESTAMP)
    """
    execute_sqlite_update(db_path, query, (internal_id, role, content))
```

### **2. API Endpoints (All use thread_slug)**

```python
# All endpoints accept thread_slug as 'thread_id' parameter

@thread_bp.route('/messages/save', methods=['POST'])
def save_messages():
    thread_slug = request.json['thread_id']  # e.g., '1762664086386'
    messages = request.json['messages']
    
    # Use helper function
    for msg in messages:
        save_message_to_thread(thread_slug, msg['role'], msg['content'])

@thread_bp.route('/messages/get', methods=['GET'])
def get_messages():
    thread_slug = request.args.get('thread_id')

    messages = get_messages_for_thread(thread_slug)
    
    return success_response({'messages': messages})
```

## 🎯 Summary: Best Practices

### ✅ **DO:**

1. **Use `thread_slug` everywhere in APIs**
   - Request parameters: `thread_id: "1762664086386"`
   - Response data: `id: "1762664086386"`
   - URL paths: `/threads/1762664086386/messages`

2. **Use `thread_slug` in external-facing tables**
   - `thread_assignments.thread_slug`
   - `synergy_sessions.thread_ids` (JSON array)

3. **Use `threads.id` ONLY for internal database JOINs**
   - `messages.thread_id` → `threads.id`
   - Never expose `threads.id` to frontend

4. **Create helper functions** that accept thread_slug and handle the internal ID lookup

### ❌ **DON'T:**

1. **Don't expose `threads.id` to frontend**
   ```javascript
   // ❌ WRONG
   thread.internal_id = 2;  // Don't send this to frontend
   ```

2. **Don't use `threads.id` in APIs**
   ```python
   # ❌ WRONG
   @app.route('/threads/<int:thread_id>')  # Don't use integer ID
   ```

3. **Don't store `threads.id` in external systems**
   ```python
   # ❌ WRONG
   synergy_session.thread_ids = [1, 2, 3]  # Use thread_slugs!
   ```

## 🔍 Why This Architecture is Best

### **Comparison:**

| Approach | Pros | Cons |
|----------|------|------|
| **thread_slug as Primary ID** ✅ | Stable, portable, user-facing, works in URLs, consistent across systems | Need internal lookup for DB JOINs |
| **Database `id` as Primary ID** ❌ | Fast DB JOINs | Changes on rebuild, not portable, implementation leak, can't be generated frontend |
| **UUID as Primary ID** 🤷 | Very stable, industry standard | Longer strings, more storage, overkill for timestamps |

**Decision: `thread_slug` (timestamp-based) is perfect for this use case**

- ✅ Unique (timestamp in milliseconds)
- ✅ Sortable (chronological order)
- ✅ Human-readable (somewhat)
- ✅ Short (13 digits vs 36-char UUID)
- ✅ Already implemented everywhere
